# DR-XAI Platform

A web application for **ophthalmologists** to read retinal fundus photographs
with AI assistance. It grades diabetic retinopathy on the ICDR 0–4 scale,
records laterality and clinical notes per eye, and exports a report carrying
both the model's reading and the clinician's own.

> **No diagnostic model is connected.** Every result the platform produces today
> is randomly generated by a stub backend. Results are recorded as simulated in
> the database, labelled as simulated everywhere they appear in the interface,
> and watermarked on every exported PDF. **Not a medical device. Not for
> clinical use.**

---

## What it does

- **Credential-gated access.** There is no self-service sign-up. A clinician
  applies through a public form with proof of qualification; an administrator
  verifies it against a medical register before an account is created.
- **Per-eye records.** Every diagnosis is filed against a patient and a specific
  eye (OD/OS), so a scan can be read against earlier scans of the same eye.
- **Provenance on every result.** Which model and which version produced it,
  stored per row — so when real performance figures exist, any report can be
  tied to the exact version behind it.
- **Audit trail.** Sign-ins, patient-record access, diagnosis runs and
  administrative changes are all recorded with the actor, the record touched and
  the origin address.
- **Authenticated images.** Retinal photographs are never publicly addressable.
  They are served only through a route that checks the requesting clinician owns
  the record.

## Stack

| | |
|---|---|
| Backend | FastAPI · SQLAlchemy (async) · Alembic · Pydantic v2 |
| Frontend | React 19 · Vite · Tailwind 4 (`@theme`, no config file, no shadcn) |
| Database | PostgreSQL (Supabase, transaction-mode pooler) |
| Auth | JWT bearer tokens, bcrypt password hashing |
| Motion | GSAP + ScrollTrigger |

## Running it locally

**Requirements:** Python 3.12+, Node 20+, and a PostgreSQL database
(Supabase or local). SQLite also works for a quick look.

```bash
# 1. backend
cd backend
python -m venv venv
./venv/Scripts/activate          # Windows;  source venv/bin/activate on macOS/Linux
pip install -r requirements.txt
cp .env.example .env             # then fill it in — see the comments inside
python -c "import secrets; print(secrets.token_urlsafe(64))"   # SECRET_KEY
alembic upgrade head
python seed.py                   # creates the first admin from SEED_ADMIN_* in .env
python run.py                    # http://127.0.0.1:8000  (docs at /docs)
```

```bash
# 2. frontend, in a second terminal
cd frontend
npm install
npm run dev                      # http://localhost:5173
```

The Vite dev server proxies `/api` to `http://localhost:8000`. To point it
somewhere else, set `VITE_BACKEND_ORIGIN` in `frontend/.env.local`.

## Configuration

Everything is environment-driven. `backend/.env.example` documents every
variable; copy it to `.env` and fill it in. **`.env` is gitignored and has never
been committed.**

The variables that matter most:

- `SECRET_KEY` — required, no default. The app refuses to start without it.
- `DATABASE_URL` — for Supabase use the **pooler** connection string
  (`postgresql+asyncpg://postgres.<ref>:<pw>@aws-…pooler.supabase.com:6543/postgres`),
  not the direct `db.<ref>.supabase.co` host, which is IPv6-only.
- `FRONTEND_ORIGINS` — comma-separated. Must not be `*`.
- `ENVIRONMENT` — set to `production` in a deployed environment. It tightens
  CORS and makes `seed.py` refuse to run.
- `MODEL_BACKEND` — `stub` today.

## Connecting a real model

One class, one registry entry, one environment variable. The full input/output
contract is documented at the top of
`backend/app/services/model_service.py` — including what the bytes you receive
have already had done to them, the value ranges you must return, threading
guarantees, and how failures are surfaced. Nothing else in the codebase needs
to change.

## Status and limitations

This is pre-release software built alongside an unfinished model. Known and
deliberate:

- Uploaded images are written to `backend/uploads/` on local disk. Supabase
  Storage is wired but deferred until the model is finished. **On a host with an
  ephemeral filesystem, uploads do not survive a restart.**
- JWTs are stored in `localStorage`, which is readable by any injected script.
  Moving to httpOnly cookies means adding CSRF protection and a refresh flow.
- There is no automated test suite yet.
